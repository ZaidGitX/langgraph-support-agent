What it is

An agentic CI/CD and DevSecOps platform. Point it at a GitHub repository or a local folder and a team of LLM-assisted agents clones it, works out the tech stack, scans it, builds it, tests it, containerises it, deploys it, tests the running app, asks a human for approval and produces a PDF report. All of it runs on the local machine.

devsecops-backendFastAPI + LangGraph agents + two MCP servers (scanner :8051, docker :8052). Python 3.12/3.13.
devsecops-frontendReact 19 + Vite + Tailwind v4 + shadcn/ui + Zustand. Live view of every run over SSE.
Deterministic thresholdsGreen / orange / red per stage from fixed thresholds (Admin › Pipeline defaults, factory values in .env). The LLM never decides.
Works without an LLMChoose provider none and every agent falls back to rules.

The project was formerly called CIP. The folders are now devsecops-backend and devsecops-frontend, and settings accept the new DEVSECOPS_* names as well as the old CIP_* / cip_* ones. A few identifiers keep the old prefix on purpose: UAT container names (cip-uat-…), the .cip/ report folder inside scanned code, and the ~/.cip/tools folder, which is still used when it exists.

How the pieces cooperate

  1. POST /pipelines/start creates a run document, then launches the graph as a background asyncio task (PipelineService.start).
  2. Each agent streams events (START / PROGRESS / COMMAND / END / ERROR / SKIPPED) into the event log (SQLite, or PostgreSQL when database_url is set); GET /pipelines/{id}/stream serves them as server-sent events.
  3. When an agent calls LangGraph interrupt() the graph pauses; the run is saved as WAITING_INPUT or WAITING_APPROVAL with a pending question. The UI shows a card; the answer is posted and the graph resumes with Command(resume=…). With PostgreSQL the paused state is a durable checkpoint, so a run that waits for a person survives an API restart.
  4. When the graph ends, the final state is stored (the runs table, or data/runs.json), and Docker images and heavy folders are cleaned up. At most max_concurrent_runs runs execute at once.

Human-in-the-loop (HITL)

Four pause points. Each calls LangGraph interrupt(), so scanners and builds never rerun on resume.

PauseStatusEndpoint to resumeEffect
QuestionnaireWAITING_INPUTPOST /pipelines/{id}/answersAnswers are validated against the questionnaire; unknown, coming-soon or locked answers fall back to the pre-filled value.
Security reviewWAITING_APPROVALPOST /pipelines/{id}/approvalOnly when the security checks are red (above a threshold); comment required. Approve → continue (the run stays red). Reject → the run fails. Switch off with option security_review: false.
Release review (before UAT)WAITING_APPROVALPOST /pipelines/{id}/approvalAlways when UAT runs; a pop-up with every stage's colour, the numbers and what happens next. Comment required to reject, and to approve while something is red. Rejection fails the run.
Change request for ProdWAITING_APPROVALPOST /change-requests/{cr}/decision or POST /pipelines/{id}/approvalApprover role. Approve → deploy to Prod with a sanity test and an automatic rollback. Reject (reason required) → Prod untouched and the run fails. Never approved by the queue's auto_approve.
Paused runs live in memory. The checkpointer is MemorySaver. If the API restarts, any run that was RUNNING or waiting is marked STOPPED at start-up (stop_unfinished_runs).

Tool loop

agents/tool_loop.py binds tools to the LLM, executes the calls it makes, feeds back results (truncated to 12,000 characters) and stops at a final answer or max_steps. Every tool call is streamed to the UI. If the step limit is hit it returns notes so the next self-healing attempt can build on them.

Workspace tools

All paths are resolved inside the run's workspace; anything outside raises an error. Tools: list_files, read_file, run_command, write_file, install_toolchain. Commands run in a shell (cmd.exe on Windows) with a 30-minute default timeout; on timeout or stop the whole process tree is killed.

Routing

After the designer (or planner in quick mode) every stage node routes through next_node: it reads execution_plan[step_index]. component_lanes fans out one Send per component. If stopped_at is set, the run jumps straight to report_agent.

lanes_done collects each lane's gates. Only an execution failure (build crashed, Docker down, no Dockerfile) stops the pipeline. A check above a threshold never stops it: the stage turns red and, for security, a human reviews.

Quality gates

Computed in utils/quality_gates.py from the thresholds the run started with (Admin › Pipeline defaults over the .env factory values). Each stage gets a colour: green nothing found, orange findings within the thresholds, red above a threshold. A threshold never fails a stage or the run. Lint findings (code_quality) are reported but never turn a stage red.

Self-healing

Read the log → find the root cause → fix → retry, up to self_heal_attempts times. The LLM may change build files, test setup, Dockerfiles or scanner installs; it is told never to change application logic or test assertions.

Where scanners live

Everything installs into devsecops-backend/.scanners (own venv + binaries via scripts/install_scanners.py), never into the API venv: Semgrep pins old opentelemetry/protobuf/mcp versions that break FastAPI and the LangChain packages. CodeQL (~1 GB) is opt-in with --codeql. Custom rules: scanner_mcp/semgrep_rules.yml and gitleaks.toml (hard-coded credential detection).

MCP servers

Both are FastMCP servers over SSE, started by the API at start-up when not already reachable (start_mcp_servers=false to run them elsewhere).

The container applies them on its first start; the API applies any that are missing at start-up (advisory lock, recorded in schema_migrations), so the same files also bring RDS or an existing server up to date. Add a new numbered file for every change; never edit an applied one. The LangGraph checkpoint tables are created by the library.

Cleanup. After a run ends (cleanup_after_run=true) node_modules, venvs, target, .gradle and caches are deleted from the workspace, scanner temp folders older than one hour are removed, and the run's Docker images are untagged. UAT containers stay running. Stopping a run also removes its containers and network. Retention: every six hours the workspace/ folder of runs that finished more than workspace_retention_days (default 7) days ago is deleted; reports, test results and the run record stay, and runs that are running or waiting are never touched.

Task ids look like <app-slug>-YYYYMMDD-HHMMSS-xxxx. Container and network names contain the last 12 characters of the task id (run_key), which is how the dashboard finds the live URLs of a run.

Key mechanics

  • Live run: usePipelineStore opens an EventSource on /pipelines/{id}/stream, derives per-step status from events and reloads the full run when the stream ends or pauses. Re-opened streams use the last event id to avoid duplicates.
  • ⓘ step info: hover shows a summary from /pipelines/step-docs; click opens the full HTML step report in a new tab.
  • API access: one axios instance (apiRepository) with base /api; the Vite dev server (or Caddy on a server) proxies /api to http://127.0.0.1:8000 (override with DEVSECOPS_API_URL) and strips the prefix. The signed-in token is sent on every request, and a 401 signs the user out. Error messages come from FastAPI's detail; structured errors (for example the missing-tools 409) keep their fields.
  • Theme: dark by default. Appearance in the sidebar offers light and dark presets (GitHub Light, Solarized, Sepia, Nord, Dracula, Monokai, high contrast, …) and a custom theme from three colours. It is stored under devsecops-ui-theme in the browser. The sidebar collapse state is also remembered per browser.

Sign-in & roles

Every API route except /health and /auth/login needs a signed-in user. core/auth.py uses only the standard library.

RoleCan
viewerRead everything: runs, dashboard, reports, tool status
operatorAlso start and stop runs, answer the questionnaire
approverAlso approve or reject the security review, the Release review and change requests
adminAlso change Settings and LLM providers, repair scanners, install tools, manage users (Users page), read the audit log
  • Passwords are PBKDF2-SHA256 (200,000 rounds, random salt) in data/users.json. Five wrong attempts for a name block it for 60 seconds. Unknown names take the same time as wrong passwords.
  • Tokens are HS256 signed (JWT format), valid auth_token_hours (12). The signing key is auth_secret_key or a generated .auth.key. The role is read from the user store on every request, so deleting a user or changing a role takes effect at once.
  • First start. If there are no users, admin is created with the password admin (or admin_password). The default, a password that breaks the policy, and every password an admin sets (new user, reset) must be changed at the next sign-in: until then the API answers 403 password_change_required to everything but /auth/me and /auth/password, and the UI shows the Change password page.
  • Password policy. At least 8 characters with an upper-case letter, a lower-case letter, a digit and a special character (core/auth.py PASSWORD_RULES, shown by GET /auth/password-policy). Enforced by the API, the UI, manage_users.py and the setup check.
  • Approvals are signed. The approver recorded on a security review or UAT approval is the signed-in user; the name sent by the client is ignored.
  • Audit. audit_log (PostgreSQL) or data/audit.log: sign-ins, failures, denials, every POST / PUT / DELETE, user changes. Admins read it at GET /auth/audit.
  • Switching it off. auth_enabled=false makes every caller a local admin and logs a warning. Use it only on a private laptop.
  • Command line. python scripts/manage_users.py list | add NAME --role R [--name --email] | update NAME [--role --name --email] | passwd NAME [--temporary] | delete NAME (asks for the password).
  • LLM audit log. Every prompt and response (services/llm_audit.py, a LangChain callback on every model) goes to runs/<id>/llm_audit.jsonl (calls outside a run: data/llm_audit.log), secrets masked, 200 KB per entry. Every signed-in user can read it.

What you see

  • Start page, last step: a banner. Green when everything required is there. Install rules

  • POST /tools/{id}/install is admin-only, runs one install at a time per tool, and only runs commands from the manifest.
  • Toolchains are downloaded with toolchain_installer.ensure. auto_install_toolchains=false stops runs from downloading on their own; an admin then installs them under Settings > Tools.
  • System tools run their apt command only when allow_system_install=true, on Linux, with sudo -n. Otherwise the answer is 403 with the command to run yourself.
  • After installing Docker on Ubuntu, restart the API so it picks up the new docker group.

Pipeline rules & skills

The shape of a guided pipeline is data, and the prompts the LLM gets are files. Both can be reviewed and changed without touching Python. Pass or fail stays in the quality gates in code.

Stage rules: config/devops_flow.yml

Each stage has a when: expression, a list of reasons: for being left out, and locked: true for the stages that are always on (scan, security_review, report).

- id: functional_tests
  node: functional_test_agent
  when: container and "functional" in tests
  reasons:
    - {when: container, text: functional tests not selected}
    - {text: nothing is deployed}          # the last reason has no 'when': it is the default

Expressions are parsed with ast and run by a small interpreter that knows and / or / not / == / != / in / not in, literals and these names: container, has_components, tests, uat, approval_before_uat, registry, deploy_as. Calls, attributes, arithmetic and imports are rejected, so the YAML cannot run code. A test runs the previous hard-coded Python rules against the YAML for more than 1,800 combinations of answers and requires identical stages and skip reasons.

Per-repository overrides: nexus.yml

# in the root of the scanned repository
stages:
  ui_tests: {enabled: false, reason: this service has no web UI}
self_heal_attempts: 1          # 0-3

A repository can only switch stages off, never the locked ones. Unknown keys, unknown stages, bad values and files over 20 KB are ignored and reported as warnings in the "Derive the pipeline" step. A broken file never stops a run.

Target environments, EC2 deploys and Prod

Admin › Target environments sets where Dev (deploy to dev, the functional and UI tests), Test (UAT) and Prod run: Local Docker, AWS EC2 over SSH, Azure or GCP. Azure and GCP are stored but not deployed to yet. Settings keys env:dev|test|prod, secrets sealed (services/environments.py).

  • AWS EC2. Server IP/DNS, SSH user and port, the private key file (kept in memory only), app port, app environment variables. Access keys only for Verify AWS (boto3: STS identity, the instance, its security groups for the SSH and app ports).
  • Test connection (asyncssh): user, OS, Docker, disk, whether the platform reaches the app port. The first success pins the host key; a changed key blocks deploys. Prepare server installs Docker and adds the user to the docker group.
  • Deploy (services/remote_deploy.py, DeployAgent): docker save | gzip over SSH into docker load (skipped when the image ID is already there); containers cip-<env>-<app>-<component> on network cip-<env>-<app>, --restart unless-stopped; the running version is renamed -previous and stopped; health from the platform, else curl on the server (security group warning); a crash loop fails within seconds; on failure the new containers are removed and the previous ones restarted and checked.
  • Prod. Only while Enable Prod deployments is on and Prod is set up: the questionnaire asks prod; stages change_request (ChangeRequestAgent) and deploy_prod (ProdDeployAgent) follow the UAT deploy. The change request CR-YYYYMMDD-NNN holds the evidence (gates, findings, tests, UAT result and approver), a low / medium / high risk with reasons, the implementation and rollback plans, and a timeline.
  • Sanity test. The start page plus the GET pages / API paths that passed the functional tests in Dev (at most 20) must answer below 500. A failed start or sanity test rolls back automatically. Change request status: PENDING_APPROVAL → APPROVED → DEPLOYING → COMPLETED | ROLLED_BACK | FAILED, or REJECTED / CANCELLED (run stopped).
  • Storage. data/change_requests.json or the change_requests table (db/migrations/003_change_requests.sql). UI: Change requests (/change-requests) and the decision dialog on the run page. The PDF report has a Prod section.
  • Testing without AWS. scripts/tests/fake-ec2/Dockerfile: sshd + its own Docker engine. tests/test_remote_deploy.py (opt-in, FAKE_EC2_KEY) covers deploy, replace, a broken version rolled back, and a Prod sanity failure rolled back.

Event-driven runs (sel-nexus queue)

sel-nexus asks for a run with POST /queue/requests; the request waits in a queue until a run slot is free, then runs like any other. The result is written back to the request and, optionally, POSTed to a callback URL.

  • Request. Required: repository (GitHub / GitLab URL), and access_token for a private repository (a public one needs none; a private one without it is refused with 400). Optional: branch, llm_provider, mode (guided / quick), answers (questionnaire; empty = the pre-filled answers), auto_approve, callback_url, reference, options. The pipeline name is sel-nexus-<app_name>-DD-MM-HH-MM (without app_name: the repository's name).
  • Poller. services/queue_service.py runs in the API every 5 seconds: it starts the oldest QUEUED requests while fewer than max_concurrent_runs runs execute, answers the questionnaire from the request, approves the security review and the UAT approval when auto_approve is true (recorded as sel-nexus (auto_approve)), and otherwise shows WAITING_APPROVAL until a person decides in the UI. queue_enabled=false switches it off.
  • Status. QUEUED → STARTING → RUNNING ⇄ WAITING_APPROVAL → COMPLETED | FAILED | STOPPED, or CANCELLED. result.overall is the pipeline result (PASS / FAIL / INCOMPLETE).
  • Result. Overall result, stage summary, findings per severity, test summary, root cause, report URL; for a failed run (or one with critical / high findings) also the remediation spec (remediation_markdown, remediation_url). The callback is sent after the spec is ready, three tries.
  • Storage. data/queue.json, or the queue_requests table (db/migrations/002_queue.sql; claimed with FOR UPDATE SKIP LOCKED). Requests claimed but not started when the API stopped go back to the queue.
  • Token. Sealed with the settings key until the run starts, then deleted; never returned. A request that never started (failed to start, cancelled) keeps it for Retry. A public-repository request has no token and can be retried once, while it never ran.
  • No sign-in. POST /queue/requests and GET /queue/requests/{id} are open by design: only the sel-nexus server (and your own IP) may reach port 80.
  • UI. Queued requests (/queue): status, position, run link, PDF, remediation spec; operators cancel / stop / retry.
  • Simulator. New test request on that page sends a request built from every field (questionnaire answers from GET /pipelines/questionnaire) to the real endpoint, then follows it: status, the JSON sel-nexus polls, and the callback, received by a built-in test receiver (/queue/test-callback/{token}, known tokens only, in memory). Copy as curl masks the token.
  • Prod. auto_approve never approves a change request; the result carries change_request and, once deployed, prod_url.

Install & run

Prerequisites

Run scripts\setup_windows.ps1 to see what is missing (add -Install to install it with winget). Windows 10/11, Python 3.12 or 3.13 (use a real install; a venv breaks if its base Python is removed), Node.js, Git, Docker Desktop (for containers and image scans), Chrome (for UI tests), and an LLM key unless you use provider none.

One click

start_agentic.bat

It first runs scripts\setup_windows.ps1 -Preflight: Python, Node.js, Git, Docker Desktop running, devsecops-backend\.env present (created from .env.example if missing) and ports 8000 / 5173 free. If anything is missing it lists what to do and stops; a missing Chrome is only a warning. start_agentic.bat --skip-checks bypasses the check.

Then it picks Python 3.12/3.13, creates or repairs devsecops-backend\.venv (an existing venv folder is used as-is), installs requirements, installs scanners once into .scanners, starts the API on :8000 (which starts both MCP servers), runs npm install if needed, starts the app on :5173 and opens the browser. Edit devsecops-backend\.env to add your keys, then restart the API.

cd devsecops-backend

:: API on :8000 (no --reload: runs write into devsecops-backend\runs and would restart it)
.venv\Scripts\python -m uvicorn main:app --port 8000

:: frontend, second window
cd devsecops-frontend
npm install
npm run dev

First run

  1. Open http://localhost:5173 and sign in as admin / admin (or admin_password from .env), then choose a new password. The user is created only once: later changes to admin_password have no effect, so reset it with .venv\Scripts\python scripts\manage_users.py passwd admin (in devsecops-backend). Add more users on the Users page.
  2. Admin → LLM providers: add a model and press Test, or choose none.
  3. On the Pipeline page enter a GitHub / GitLab URL or local folder, keep Guided mode, and start. For a private repository the form asks for a read-only access token (GitHub: Contents read-only; GitLab: read_repository). The last step checks the tools this run needs and shows how to install anything that is missing.
  4. Answer the questionnaire, review the security reports, and approve the UAT deploy when asked.
  5. Open the Dashboard for the result, live app URLs, the PDF and the test report.

Deploy & operate

The platform runs directly on a machine and uses its installed tools and Docker engine. Local is Windows; the dev server is an Ubuntu EC2 instance. Run it on a dedicated machine: it executes code from the repositories it scans.

Ubuntu 22.04 / 24.04 (EC2)

Instance: Ubuntu 24.04 (Canonical AMI), x86_64, at least t3.large (8 GB RAM) with SonarQube (t3.xlarge is comfortable; 4 GB is enough with --no-sonarqube), 50 GB gp3 root volume. Security group: SSH and port 80 from your IP only; add 32768-60999 from your IP to open deployed UAT apps.

git clone -b <branch> <repository> && cd devops-sel-nexus

One run does three things, in this order:

  1. Prerequisites - Ubuntu 22.04/24.04, root or passwordless sudo, RAM (8 GB with SonarQube, else 4), free disk (40 GB with SonarQube, else 25; 5 on a re-run), HTTPS to pypi / nodejs.org / Docker Hub / GitHub, a full checkout, devsecops-backend/.env with the keys of llm_provider (and, optionally, an admin_password that meets the password policy), and ports 80 / 8000 / 9000 / 5432 free (or held by the platform itself). If anything is missing it prints a numbered "Do this first" list and stops - nothing is installed. A missing .env is created from .env.example for you to fill in.
  2. Install - it prints skip / install per component, then installs what is missing: Python 3.12+ venv and requirements, git / Docker / Chrome / C/C++ build tools for native npm and pip modules (config/tools.yml; Chrome is skipped on ARM), the scanners, Node + the frontend build, Caddy (replacing an nginx set up by an older version), PostgreSQL and SonarQube in Docker (admin password changed, token written to .env), and DEVSECOPS_HOST_IP from the EC2 metadata so deployed app links use the public IP (with --domain: DEVSECOPS_DOMAIN and https://<container>.<domain>).
  3. Start and check - the devsecops-backend service behind Caddy; then it checks the API, Caddy, SonarQube and one real LLM call, and prints the URL.
  • Options: --no-sonarqube, --no-postgres, --public-host H, --domain NAME (--server-name still works), --service-user, --no-docker --no-chrome --no-scanners --no-frontend --no-caddy --no-service (--no-nginx still works). --with-postgres / --with-sonarqube are still accepted (both are on by default). MIN_RAM_GB / MIN_DISK_GB change the thresholds, NET_CHECK=0 skips the network check.
  • Do not copy .venv, .scanners, node_modules, data/ or runs/ from Windows: they are built for Windows or tied to keys of that machine. Only .env.
  • On 22.04 the script adds the third-party deadsnakes PPA for Python 3.12. The Node download is checked against nodejs.org's SHA-256 list.
  • It sets up devsecops-backend.service (127.0.0.1:8000, NoNewPrivileges) and /etc/caddy/Caddyfile, which serves the built frontend and proxies /api (flushing the live logs at once). With --domain Caddy gets Let's Encrypt certificates for the domain and, on demand, for each running UAT app at https://<container>.<domain>; without it there is no TLS. Keep ports 80/443 closed to everyone but your network (security group or VPN).
  • Changing .env later: sudo systemctl restart devsecops-backend. Logs: journalctl -u devsecops-backend -f.

Security notes

  • Sign-in and roles. See Sign-in & roles. The API still runs commands from scanned repositories on the machine, so keep it on a private network or behind a VPN. The local MCP servers have no authentication of their own and listen on localhost.
  • Installing tools is powerful. The Install button only runs fixed commands from config/tools.yml (never text from a request), only for admins. System tools (apt) need allow_system_install=true and passwordless sudo, which is root-equivalent: leave it off unless you need it. Membership of the docker group is root-equivalent too: use a dedicated machine.
  • Default passwords. The platform and SonarQube both start with admin / admin and force a new password at the first sign-in: sign in to both right after installing.
  • Unauthenticated queue. /queue/requests has no sign-in (sel-nexus integration): anyone who reaches the API can start runs, which execute repository code on the server. Allow port 80 only from the sel-nexus server and your own IP.
  • LLM log. Prompts contain code and findings of the scanned repositories; secret values from .env are masked, but treat the files like the run reports.
  • Network exposure. PostgreSQL and SonarQube bind to 127.0.0.1; Caddy is the only public side (the app, /api, /sonar and, with a domain, the UAT apps). Use --domain for HTTPS (or a load balancer in front) and restrict ports 80/443 with a security group or VPN.
  • Audit. Every state-changing call, sign-in, failed sign-in, denied request and user change is recorded with the actor. Request bodies are not recorded because they may contain secrets.
  • The API runs arbitrary commands. Build, test and install commands come from the target repository (and from the LLM) and are executed in a shell on the host. Only point it at code you trust, or run it in a disposable VM.
  • Credentials. Secrets saved in Settings are Fernet-encrypted; the API never returns them. Repository access tokens (from the start form, or github_token / gitlab_token) reach git as an HTTP header through its environment (GIT_CONFIG_*), so they are not on the command line, in the clone's .git/config, the run, its checkpoints, logs or reports; a token from the form is held in memory only until the clone ends. URLs with credentials in them are refused. Keep .env and .settings.key out of git (both are ignored).
  • Path safety. Workspace tools reject paths outside the run workspace; screenshot and test-result endpoints validate file names and reject path separators in the task id.
  • UAT on a server. UAT containers can bind 0.0.0.0 on a random port (32768-60999); DEVSECOPS_HOST_IP (set by setup_ubuntu.sh) makes their links use the public IP. With DEVSECOPS_DOMAIN they are served by Caddy at https://<container>.<domain> instead (a certificate only for a running cip-* container published on 0.0.0.0), so the high ports can stay closed. Treat them as reachable by anyone the security group lets in.
