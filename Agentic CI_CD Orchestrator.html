Agentic CI/CD Orchestrator

A LangGraph-orchestrated, fully autonomous DevOps system: one supervisor agent interrogates a freshly checked-out repo, asks the user only what it cannot infer, derives a pipeline configuration, and fans work out to specialist subagents that build, scan, package, containerize, release, deploy, test, and stage UAT across local and AWS environments.

Status Proposed Date 2026-10-05 Cloud scope AWS only engine: Jev (router/selector) workers: GPT-6 Astra tool bus: MCP

Context

The trigger is a Git event, not a ticket: on push or PR merge, the orchestrator checks out the code, retrieves what the knowledge base already knows about the ecosystem (languages, build tools, dependency graph, prior run history), and opens a human-in-the-loop exchange only for the gaps. Its output is a pipeline configuration — a stage DAG spanning build + scans (SAST, DAST, dependency, vulnerability, secrets), package, containerize, release, deploy, test-script execution, and UAT promotion — which it then executes through subagents holding real tools.

Two forces shape the design. First, the control flow is genuinely stateful and cyclic (clarify loops, remediation loops, approval gates), which rules out linear chain frameworks and favors an explicit state graph. Second, agents that run shell commands, push images, and deploy to AWS need isolation, scoped credentials, and durable sessions — the problem Amazon Bedrock AgentCore (GA 2026) was built for: microVM runtime sessions with direct shell execution for deterministic ops, a Gateway that fronts tools as MCP servers, per-agent Identity, and managed Memory.

Jev and GPT-6 Astra are used here as you specified: Jev as the fast selection/routing engine governing edge transitions, Astra as the heavyweight reasoning model inside each worker. The architecture is model-agnostic — both are swappable bindings in config, not structural commitments.

1 · Control plane — the LangGraph state machine

Every node reads and writes one shared PipelineState; Jev governs the conditional edges (skip, route, retry, escalate). Human interaction is a first-class graph primitive — interrupt() pauses the run durably at the checkpointer, and the user's answer resumes it, which is what makes the same graph work in chat, CLI, or a dashboard.

The shared state object

One schema carries the run end to end — this is the "environment state space embedding the A→Z completion of the pipeline" in your framing. Fan-in from parallel subagents is an append reducer, so concurrent stage results merge without clobbering.

class PipelineState(TypedDict):
    run_id: str                       # thread_id for the checkpointer
    repo: RepoProfile                 # languages, build tools, dependency graph
    ecosystem: dict                   # KB retrieval results (graphify graph + vector)
    open_questions: list[Question]    # drives interrupt() — empty ⇒ Jev skips clarify
    answers: dict                     # user inputs: env targets, test depth, release policy
    pipeline: PipelineConfig          # Jev-ranked stage DAG + per-stage tool bindings
    stage_results: Annotated[list[StageResult], operator.add]   # fan-in reducer
    env_state: EnvSnapshot            # A→Z pipeline completion state, local + AWS
    approvals: dict[Gate, Decision]   # pipeline-approval, deploy, UAT sign-off
    attempt: dict[str, int]           # bounded retry counters per stage

2 · System planes — where everything runs on AWS

The orchestrator graph is the brain; this is the body. Control and worker planes run as Bedrock AgentCore Runtime sessions (isolated microVMs, long-lived, resumable). Every tool reaches the world through MCP servers fronted by AgentCore Gateway, and every agent gets least-privilege IAM via AgentCore Identity — a subagent that builds images cannot touch a production cluster.

4 · Mapping to the reference agent harness

Your harness reference decomposes an agent into five stages plus a memory layer. This architecture is that harness, instantiated for DevOps:

Harness stageInstantiation in this system
1 · Input & contextWebhook payload, checked-out repo, run history, prior answers — assembled into PipelineState at graph entry.
2 · Retrieval & candidatesdiscover_ecosystem: hybrid retrieval — graphify knowledge graph for structural questions (dependency paths, impacted modules, god nodes, community boundaries) + OpenSearch vectors for unstructured code/docs; candidate pipeline configs generated, not assumed.
3 · Jev selection layerJev as the fast ranking/classification model on every conditional edge: pick the pipeline config, filter irrelevant stages, route pass/fail/remediate, decide retry vs. escalate. Cheap tokens where reasoning depth isn't needed.
4 · Agent (planning & reasoning)Orchestrator planning node plus GPT-6 Astra inside each stage subagent — the expensive model only where failure analysis and plan repair genuinely need it.
5 · Execution & validationMCP tool calls inside AgentCore microVMs; quality_gate validates evidence (exit codes, scan reports, test results) before any edge advances; bounded retries.
Memory layerShort-term/thread: Aurora checkpointer. Long-term/semantic: OpenSearch vectors + AgentCore Memory (preferences, past decisions). Structural/graph: graphify knowledge graph of the codebase, refreshed per checkout. Artifacts: S3. Retrieval → Jev → injected context — the harness's "vector DB + structured storage + optional graph" triad, with the graph not optional here.

5 · ADR-001 — Orchestration spine

Status: Proposed · Deciders: Lead Engineer · Scope: AWS only

Decision

Use LangGraph (v1.x) as the orchestration spine, hosted on Amazon Bedrock AgentCore for runtime isolation, tool gateway (MCP), identity, and memory — rather than encoding the pipeline in Step Functions or adopting a framework-native swarm.

Options considered

Trade-off analysis

  • A vs B: Step Functions excels when the pipeline is fixed; the whole point here is that the pipeline is derived per run from repo state + user answers. A dynamic DAG wants a programmable graph, not ASL. Keep Step Functions in reserve for fully-hardened, no-LLM sub-pipelines later.
  • A vs C: CI/CD is order- and evidence-sensitive; supervisor > swarm. LangGraph's supervisor pattern has the strongest native support in 2026, and the guidance for 5+ workers (hierarchical supervisors) gives a clean growth path — the stage executor becomes a sub-supervisor if stages gain internal crews.
  • Jev/Astra split is the cost architecture: routing, ranking, and gate decisions are classification-shaped (Jev); plan synthesis and failure diagnosis are reasoning-shaped (Astra). Collapsing both into one model either overpays on every edge or under-reasons on every failure.
  • Determinism boundary: anything a Makefile can do, the microVM shell does — the LLM decides what and whether, the shell does how. This is the single biggest lever on cost, latency, and reproducibility.

6 · SDLC & Agile alignment

Build / Test (shift-left)

SAST, SCA, secrets, and vulnerability scans run inside the build stage, not after it — a failed scan is a failed build, caught before packaging.

Release / Deploy

Signed images with SBOMs in ECR; gated promotion through dev → staging → UAT mirrors a Definition of Done per environment.

UAT = sprint review artifact

The UAT stage produces a live environment plus evidence bundle — exactly what a sprint review demos and a product owner signs off.

Operate / Maintain = retrospective loop

CloudWatch signals and run reports feed the KB and dashboard; recurring failures become backlog items, and the planner's candidates improve each sprint.

Agile fit in one sentence: the pipeline configuration is a per-iteration artifact, regenerated from the current state of the codebase every sprint, instead of a static YAML that quietly rots.

7 · Consequences

  • Easier: onboarding a new repo (the system interviews it), evolving pipelines (regenerate, don't refactor YAML), auditing (checkpointed state + MCP logs reconstruct every run), pausing for humans (durable interrupts).
  • Harder: cost governance (needs per-run token budgets and the Jev/Astra split enforced), determinism (pin tool versions in microVM images; replay from checkpoints when debugging), trust calibration (gates start strict, loosen with evidence).
  • Revisit when: stage count or concurrency grows past a single supervisor's context (→ hierarchical supervisors); a sub-pipeline fully stabilizes (→ compile it down to Step Functions and remove the LLM from its path); multi-cloud returns to scope.
Guardrails that are non-negotiable: bounded retries per stage (no infinite remediation loops), hard token/time budget per run enforced in the dispatcher, no deploy edge past UAT, and per-agent IAM so a compromised or confused subagent cannot exceed its stage.
